PLAN DEVIATION: `tools/gen-width-tables.py` was NOT written — utf8proc already carries the exact UCD the plan asked for, and a second table would only drift from the segmentation tables ADR-0003 obliges us to use (evidence: `docs/research/t19-width-findings.md`). | Reflow | resize rewraps logical lines | ◐ | unit `[reflow]` (tests/unit/reflow_test.cpp), `[grid]` resize cases, fuzz seed `reflow.seed` | T20. No VT standard specifies reflow; this is emulator behavior, and the rules are ours. A logical line is a maximal run of rows whose successors carry `wrappedFromPrev` (recorded since T8, which is why this was a storage walk and not a rewrite). On a column change those runs are rejoined, their UNWRITTEN tail is trimmed, and the content is re-split at the new width. Only `ch == 0` is trimmed, never a printed space — erasure resets `ch` to 0 while a printed U+0020 stores 0x20, so `echo "hi   "` keeps its spaces; interior holes an application punched with CUP+EL survive because the trim walks in from the end only. A 2-column cluster is never split: reflow detects the pair from its `kWideTrailing` cell rather than re-measuring width (one source of truth), moves it whole, and lets a row end one column short. The cursor is carried by logical offset, including when it sits PAST its content — the active-prompt case. Extra rows from a narrowing rewrap are absorbed by blank rows at the BOTTOM before anything retires off the top into scrollback; without that, shrinking a window scrolls the prompt into history. Alternate screen is NOT rewrapped (the application redraws on SIGWINCH). **KNOWN GAPS:** ED/EL can erase the lead of a wide cluster and leave its trailing cell orphaned — cosmetic, not a safety issue (the fuzz target asserts the safety invariants and deliberately not this one), and it belongs to the one deferred BCE decision |
| Scrollback | history ring, viewport, memory bound | ◐ | unit `[scrollback]` (tests/unit/scrollback_test.cpp) | T21. History is stored as LOGICAL lines, not visual rows: continuation rows coalesce on push using the wrap point `Line` has carried since T8, and are re-split through `reflow()` on read at whatever width is current. That is what lets history survive a resize, and it closes the gap the Reflow row used to record. TWO caps, because a cap counted only in LINES is not a memory bound — one logical line can be arbitrarily long, so a stream that never emits a newline grows the ring forever without ever adding a line to it; cells are bounded too and a single line is clamped so it cannot eat the budget alone. Reads are bounded the same way: a window read never rewraps more than roughly (rows+1)*cols cells, so a screenful costs a screenful even when one logical line holds millions. `scrollRegionUp` now clears `wrappedFromPrev` on the new top row ONLY when the retired line was discarded — if it went to history it did not scroll away, and the continuity is real. Viewport damage is all-or-nothing while scrolled up, because `DamageList` addresses SCREEN rows and partial damage would name the wrong lines. **KNOWN GAPS:** `scrollbackAt()` exposes raw logical lines whose length is NOT `cols` (unlike `viewportRows()`, which is always exactly `cols` wide) — it has no non-test caller; T25 must use the viewport. Alternate-screen rows still enter history on a row-shrinking resize, out of chronological order (T20 behavior, documented at grid.h); `breakLine()` now at least stops them being welded onto shell output as one logical line |
| Modes | DECSET/DECRST: DECOM (?6), 1049, 2004, 2026; DECRQM | ◐ | corpus/csi/origin.case, corpus/sgr/mode.case | **T22: DECRQM (`CSI ? Ps $ p` -> `CSI ? Ps ; Pm $ y`) answers from `decrqmState()`, which reads live grid state and the capability table — there is no hardcoded answer anywhere, so a reply and the implementation cannot disagree by construction.** The 1/2 vs 3/4 split carries the honesty rule: 1 and 2 promise an application it can CHANGE the mode, 3 and 4 say the answer is fixed. So 2027 answers 3 (clustering is always on, T19), and DECAWM (?7) and DECTCEM (?25) also answer 3 — we autowrap with no path that does not, and nothing hides the cursor until T25; answering 1 would invite an application to turn them off and then misdraw. Anything unimplemented answers 0, never 2: "reset, you may set it" is the same lie as "set", it just fails one step later — mouse reporting (?1000) is the case that matters until T27. DECRQM takes exactly ONE mode; a list, a missing parameter, colon subparams, the ANSI form without `?`, and `p` without the `$` intermediate are all honest silence. Mode 2004 (bracketed paste) is a real flag here; the ESC[200~/ESC[201~ wrapping and the paste-guard are T28. Mode 2026 (synchronized output) opens and closes a batch, with the ~150 ms guard rules/vt-core.md requires so a client that sets 2026 and then blocks or dies cannot freeze rendering. The guard's clock is PASSED IN (`Grid::nowMs`, refreshed by the integrator per chunk) because src/core/ owns no clock — the same reason ReplyLimiter meters on input volume. DECRQM reports what the APPLICATION requested, not what the guard is doing: the timeout is a rendering safety net, and reporting a timed-out batch as reset would lie about state the application owns. T18: the `?`-private DECSET/DECRST seam. **DECOM** — both set AND reset home the cursor: xterm's DECOM case runs `CursorSet(0,0,flags)` unconditionally after flipping ORIGIN, so set homes to the top margin and reset to absolute row 1. (The vt100.net DECOM page describes neither motion — it only relocates where "home" *is*; the homing itself is xterm/DEC STD 070. That page does settle the other half: the cursor "cannot move outside of the margins" set, "can" reset.) DECOM also makes DSR 6 report a margin-relative row, or the save/restore round trip apps do would drift. **1049** — save cursor → switch → clear on set; switch back → restore on reset, with no clear (clearing on the way out is 1047's behavior, not implemented). **Not idempotent, deliberately:** xterm's `whichBuf` guard sits INSIDE `ToAlternate`/`FromAlternate` while the surrounding `CursorSave`/`ClearScreen`/`CursorRestore` run unconditionally, so a repeated `?1049h` really does re-clear the alternate screen (full-screen — `ClearBufRows` ignores the margins) and a cold `?1049l` really does restore a never-written slot, homing the cursor and resetting the pen. Only the CELLS are per-buffer: margins, pen, and cursor are shared (xterm ptyx.h has one set of each and only indexes two cell arrays), so a region set on the normal screen still applies on the alternate one. Two saved-cursor slots indexed by active buffer, holding position + pen + DECOM + pending wrap + shift state (xterm `CursorSave2`) but NOT the margins. A resize reshapes the inactive buffer, dropping rows off the TOP under xterm's default SouthWest gravity, and clears DECOM along with the margins (xterm `ScreenResize`). DIVERGENCE: 1049's clear uses default cells, where xterm fills with the current SGR pen — deliberately deferred so BCE stays ONE decision across ED/EL/IL/DL/SU/SD/1049 rather than half-landing here. MISSING, and two of these make output WRONG rather than merely absent: **?7 DECAWM** (autowrap is hardwired on, so `CSI ?7l` is accepted and we keep wrapping) and **?25 DECTCEM** (accepted, but the renderer will keep painting a cursor). Also missing: 47/1047/1048 (older alt-screen and save-cursor spellings), 2004 paste, 2026 sync, 2027, 2048, and every ANSI (non-`?`) mode. Unrecognised DEC modes are consumed and ignored, which stays honest only while DECRQM is unanswered — T22 must report every mode not listed here as not-recognised |
