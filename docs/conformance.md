No VT standard specifies reflow; this is emulator behavior, and the rules are ours. A logical line is a maximal run of rows whose successors carry `wrappedFromPrev` (recorded since T8, which is why this was a storage walk and not a rewrite). On a column change those runs are rejoined, their UNWRITTEN tail is trimmed, and the content is re-split at the new width. Only `ch == 0` is trimmed, never a printed space — erasure resets `ch` to 0 while a printed U+0020 stores 0x20, so `echo "hi   "` keeps its spaces; interior holes an application punched with CUP+EL survive because the trim walks in from the end only. The cursor is carried by logical offset, including when it sits PAST its content — the active-prompt case. The core decides WHAT was asked and does none of it: no clipboard, no browser, no window title is touched below src/app (CLAUDE.md's zero-deps rule). ****OSC 133 (T66, M4) — semantic shell integration**, spec `OSC 133 ; <command> [; <key>=<value> ...] ST`, verified against contour-terminal.org/vt-extensions/osc-133-shell-integration, kitty's shell-integration docs, iTerm2's escape-code reference, and cross-checked against two implementations — ghostty's `src/terminal/osc/parsers/semantic_prompt.zig` and wezterm's shipped `assets/shell-integration/wezterm.sh`. (The canonical Per Bothner proposal on gitlab.freedesktop.org is Anubis-blocked on every path including `-/raw`; the above are the substitutes.) Both ST and BEL terminate. **A** fresh line + prompt start, **P** prompt start, **B** prompt end / user input start, **C** command executed / output start, **D** command finished with an optional exit status. **`P` is implemented and that is not optional generosity:** ghostty names it `prompt_start`, and `133;P;k=i` — not `133;A` — is what wezterm's shipped integration, DomTerm's, and zsh's own `Src/Zle/termquery.c` actually emit, so handling only `A` would place ZERO marks for three real shell integrations. **`k=` is read, not skipped**, because it changes what the command means: kitty documents `A;k=s` before the PS2 prompt, and ghostty's alphabet is `i` initial / `r` right / `c` continuation / `s` secondary. Only `k=i` or an absent `k=` is a navigable command prompt; secondary, right and continuation prompts get no mark at all. Without that, every PS2 row of a multi-line command is a prompt start AND `D`'s status attaches to the last continuation row instead of the line the command began on — the precise failure the write-it-back design exists to prevent. The genuinely unknown options — `aid=`, `cl=`, `click_events=1`, `cmdline_url=` — are SKIPPED, never fatal: that list grows with every terminal that adds an extension, and dropping a visible prompt boundary because a shell learned a new key is the worse failure. The exit status is **positional, field 1 only** (`OSC 133 ; D ; 0 ; aid=…`), matching ghostty's `parseInt(i32, full, 10)` and wezterm's `\033]133;D;%s;aid=%s\007`; `D;oops;5` therefore records nothing, as it does everywhere else. **Where the mark is stored is the whole design decision**: on the `Line` (`src/core/grid/line.h`), as a bitmask on the row that HEADS the logical line, never in a side table keyed by row number. A row number is invalidated by every scroll, every eviction and every reflow, so a mark stored beside the grid would point at different text the moment the user dragged the window — the same landmine CLAUDE.md records for scrollback. On the Line it rides the three paths that already carry `wrappedFromPrev`: `Scrollback::push` ORs a continuation row's marks onto the logical line it joins, `reflow()` gathers the run's marks and re-attaches them to whichever row heads the re-split, and eviction drops the line and its mark together. A bitmask rather than an enum because **A and B normally land on the SAME line** — prompt text then the command typed after it are one logical line — so an enum would silently lose every prompt the shell also marked B on. `OSC 133 ; D`'s status is written back onto the nearest preceding `kMarkPromptStart` line, which by then is usually already in scrollback; the status parse is digits-only, overflow-checked and bounded at 2147483647 (wider than the spec's stated 0-255 range, harmlessly — ghostty is `i32` too), and a malformed, negative or overlong status is REFUSED whole (the mark still lands — the command did finish, we simply do not know how). **That backwards walk is bounded by a `m_promptOpen` flag**, not by trust: `\e]133;D\e\\` is thirteen bytes, so without the flag a megabyte of them would cost ~10⁹ line visits on the parse thread; a `D` that follows no `A` now does no work at all. **KNOWN GAP, found by T67's audit and left as T66 debt rather than fixed inside a UI task:** the flag bounds repeated `D`s, not repeated `A`+`D` PAIRS. `ESC]133;A ST` `CSI 2J` `ESC]133;D ST` is 25 bytes, and the `2J` clears the mark (see `clearRange` above) without clearing the flag — so each triple opens the flag and then walks the whole history finding nothing. A megabyte of them is ~10⁸ line visits on the parse thread: a throughput DoS, not a crash or a memory bound violation, but a real one. The fix is a stable index for the open prompt (a lines-ever-pushed counter on `Scrollback`, so the walk is proportional to the distance to the actual `A`) rather than a positional field, which cannot survive eviction — not a one-liner, and a change to T66's design. `Grid::prevPrompt`/`nextPrompt` find marks across scrollback and screen. Their index space is *shaped* like `SearchHit::line` but is **not the same space** — search enumerates `viewportRows()`, which serves rewrapped history rows whenever the viewport is scrolled up, while this always ends in the screen buffer; the two agree only at `viewOffset() == 0`, and `grid.h` says so rather than promising a translation-free coordinate. Marks are normal-buffer only: `markPrompt`/`setCommandExit` are no-ops on the alternate screen, since the scrollback is the normal buffer's history and splicing the two would name lines that do not exist. ED/EL clear marks on any fully-blanked row (`sgr.cpp` `clearRange`, beside where it already clears `wrappedFromPrev`) so a `clear` does not strand jump targets on blank rows. **NOT implemented, deliberately, and each is a real gap rather than noise:** `L` (fresh line), `N` (new command) and `I` (end prompt, terminate at EOL) are spec'd letters that stay honest silence; **`A`'s implied fresh-line is NOT performed** — ghostty's name for `A` is `fresh_line_new_prompt`, and when a command's output does not end in a newline (`printf hi`, an interrupted program) the cursor is still mid-row, so `markPrompt` marks the head of that OUTPUT line and `prevPrompt` points at output rather than at a prompt. No capability reply claims any of this — see below. ****OSC 9;4 (T67, M4) — taskbar progress**, spec `OSC 9 ; 4 ; <state> [; <progress>] ST`, terminated by ST or BEL. Verified against BOTH primary sources rather than remembered: Microsoft documents it for Windows Terminal (learn.microsoft.com, "Set the progress bar in Windows Terminal", `ESC ] 9 ; 4 ; <state> ; <progress> BEL`) and ConEmu, which originated it, documents `ESC ] 9 ; 4 ; st ; pr ST`. States: **0** remove, **1** set to `<progress>` in the default state, **2** error state (`pr` optional per ConEmu), **3** indeterminate — MS says in as many words that this state IGNORES `<progress>` — and **4**, where the two sources DISAGREE: MS calls it "Warning", ConEmu calls it "paused". Both end at the same Win32 flag (`TBPF_PAUSED`, one yellow bar), so `OscAction::Progress::Paused` is named for the flag rather than for either doc. `<progress>` is documented as 0-100 inclusive; **neither source says what an out-of-range value means, so Krait CLAMPS to 100** — a refusal would leave a stale bar asserting something else, and a bar pinned full is the only reading of "250%" that is not a lie. **An ABSENT or EMPTY state means REMOVE**, not "malformed" — `OSC 9;4 ST` and `OSC 9;4; ST` clear the bar, which is what Windows Terminal's own `AdaptDispatch` ConEmu action does (a missing state reads as 0). Refusing them was the first cut and was wrong: of the two available failures, a bar left asserting progress for a finished command with nothing able to clear it is worse than one that never appears. Everything else is refused WHOLE: the subcommand must be exactly `4` (OSC 9 with any other payload is ConEmu's notification form, which Krait does not implement), and a NON-EMPTY state must be a single digit 0-4 — `10`, `9` and `4x` all mean the sender does not mean what a legal string means, and guessing the nearest legal state would put something on a user's taskbar nobody asked for. Windows Terminal is more permissive still (`StringToUint` accepts `04` as 4); zero-padding is refused here because no emitter found produces it. A percentage that is not a number is ABSENT rather than fatal, because the state is the part the sender got right and dropping it would lose a real error bar; absent stays distinct from 0 (`percent == -1`) so the app can leave a bar where it was. | Keyboard | kitty keyboard protocol (baseline flag), win32-input-mode | ◐ | corpus/reports/kitty_keys.case, unit `[kitty]` (tests/unit/kitty_keys_test.cpp) | **T48.** All four negotiation forms: `CSI > flags u` push, `CSI < n u` pop, `CSI = flags ; mode u` set (1 replace / 2 or-bits / 3 clear-bits), `CSI ? u` query. The honesty rule does real work here and the protocol is built for it — an application SETS the flags it wants and then QUERIES to find out what it actually got, so the reply is a promise about the bytes the keyboard will send. Unsupported flags are therefore masked off ON THE WAY IN (`KittyKeyboard::kSupported`) and the query reports the truth: ask for all 31 and the answer is 1. Storing 31 and reporting 31 would promise key event types, alternate keys and associated text that `translateKey` never sends, and an application that believed it would misread every keystroke. **Only flag 1 (disambiguate) is implemented**, which is the milestone's stated baseline — flags 2/4/8/16 are the cut line. What the flag actually changes: Escape becomes `CSI 27 u` (otherwise indistinguishable from the start of a SEQUENCE, which is why editors guess with a timeout and a slow link turns Esc into Alt+something), modified Enter/Tab/Backspace become `CSI 13|9|127 ; mod u`, and Ctrl/Alt+key becomes `CSI <unshifted-codepoint> ; mod u` so Ctrl+I and Tab stop both being 0x09. Unmodified text-producing keys still send TEXT, as the protocol requires with only this flag set. The stack holds 16 and discards the OLDEST on overflow rather than refusing; popping past the bottom lands on OFF — the state every application can read — rather than on whatever was underneath. A bare `CSI u` with no private marker belongs to no protocol we speak and is honest silence. **win32-input-mode (?9001) is still ✗** for the reason recorded in the Modes row |
