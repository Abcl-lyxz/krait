A logical line is a maximal run of rows whose successors carry `wrappedFromPrev` (recorded since T8, which is why this was a storage walk and not a rewrite). On a column change those runs are rejoined, their UNWRITTEN tail is trimmed, and the content is re-split at the new width. Only `ch == 0` is trimmed, never a printed space — erasure resets `ch` to 0 while a printed U+0020 stores 0x20, so `echo "hi   "` keeps its spaces; interior holes an application punched with CUP+EL survive because the trim walks in from the end only. That last clause is a T75 fix, not a nicety: the first cut tested `!= "k=i"` and so FAILED CLOSED, dropping the mark outright for `k=`, `k=x` and `k=initial`. The spec rule for an option a terminal does not recognise is the one OSC 8's parameters already follow — ignore it — and ghostty maps an unknown kind to null, i.e. unspecified, i.e. still a prompt. Fail-closed traded a total loss of the feature (a shell that learns a new kind letter loses EVERY jump target and every exit status) for a distinction nobody asked for. Without that, every PS2 row of a multi-line command is a prompt start AND `D`'s status attaches to the last continuation row instead of the line the command began on — the precise failure the write-it-back design exists to prevent. The genuinely unknown options — `aid=`, `cl=`, `click_events=1`, `cmdline_url=` — are SKIPPED, never fatal: that list grows with every terminal that adds an extension, and dropping a visible prompt boundary because a shell learned a new key is the worse failure. The exit status is **positional, field 1 only** (`OSC 133 ; D ; 0 ; aid=…`), matching ghostty's `parseInt(i32, full, 10)` and wezterm's `\033]133;D;%s;aid=%s\007`; `D;oops;5` therefore records nothing, as it does everywhere else. **Where the mark is stored is the whole design decision**: on the `Line` (`src/core/grid/line.h`), as a bitmask on the row that HEADS the logical line, never in a side table keyed by row number. A row number is invalidated by every scroll, every eviction and every reflow, so a mark stored beside the grid would point at different text the moment the user dragged the window — the same landmine CLAUDE.md records for scrollback. On the Line it rides the three paths that already carry `wrappedFromPrev`: `Scrollback::push` ORs a continuation row's marks onto the logical line it joins, `reflow()` gathers the run's marks and re-attaches them to whichever row heads the re-split, and eviction drops the line and its mark together. A bitmask rather than an enum because **A and B normally land on the SAME line** — prompt text then the command typed after it are one logical line — so an enum would silently lose every prompt the shell also marked B on. `OSC 133 ; D`'s status is written back onto the NEWEST `kMarkPromptStart` line at or after the open prompt's floor, which by then is usually already in scrollback — **anchored at the whole grid, not at the cursor, which is a T75 fix.** The first cut started the backwards walk at `scrollbackSize() + row + 1`, so anything that moved the cursor ABOVE the open prompt between `A` and `D` made the walk start below the mark it wanted: it never reached it and either stamped the status onto the PREVIOUS command's prompt (clobbering a status that command had earned) or found nothing and dropped it. Not a hostile-input case — zsh transient prompts and powerlevel10k repaint above the prompt before `precmd` runs, so it misfired in ordinary use. The T67 bound is untouched by the change, because the bound was never the anchor: `prevPrompt` visits `min(from, absoluteLineCount()) - floor` lines either way, so anchoring at the grid trades the cursor's row for the screen height — at most `rows` extra visits, exactly the "plus at most the screen" already documented. Proved by mutation rather than argued: with the FLOOR neutralised and the new anchor kept, the flood regression case runs 9815 ms against its 5 s bound; the status parse is digits-only, overflow-checked and bounded at 2147483647 (wider than the spec's stated 0-255 range, harmlessly — ghostty is `i32` too), and a malformed, negative or overlong status is REFUSED whole (the mark still lands — the command did finish, we simply do not know how). **That backwards walk is bounded, and it takes TWO things to bound it (T68).** T66 shipped only the first: an `m_promptOpen` bool, because `\e]133;D\e\\` is thirteen bytes and without it a megabyte of them would cost ~10⁹ line visits on the parse thread. Deliberately a FLOOR and not the prompt's own index, because when `A` arrives its line is still on the SCREEN and has no stable index yet: the newest line already in history is recorded instead (`- 1`, since `head` can be screen row 0 while row 0 carries `wrappedFromPrev`, in which case `push()` coalesces the mark ONTO that history line rather than starting a new one). The walk is then proportional to lines pushed since `A` — work the remote already paid for in bytes — plus at most the screen height, and never to the size of history. Measured on the regression case (40k triples over a full 10k-line ring at 6x20): **8511 ms before, 353 ms after**. That case asserts a hard 5 s `steady_clock` bound so a regression shows up as a failing assertion rather than as a CI job killed by its own timeout — `[core][osc][shell]` "a flood of A + 2J + D triples stays bounded instead of rescanning history", with "an open prompt survives the eviction of everything around it" pinning the other half (the floor must not turn into a WRONG answer when the ring evicts underneath it), and fuzz seed `osc133-ad-flood.seed`. `Grid::prevPrompt`/`nextPrompt` find marks across scrollback and screen.
